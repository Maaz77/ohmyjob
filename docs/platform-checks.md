# Platform checks (P0)

Smoke test of the Claude Code behaviours that the plugin design depends on. Run on 2026-11-03 with Claude Code 2.1.316 (`claude --version`), model `claude-haiku-5-5`, macOS. Re-run it before each release.

**Method.** A throwaway plugin `ojtoy` (5 agents, 4 skills, a `bin/` script, and hooks that log their stdin JSON plus `CLAUDE_PLUGIN_ROOT`, `CLAUDE_PLUGIN_DATA` and `CLAUDE_PROJECT_DIR`) was driven by nested headless runs in a throwaway project:
`claude -p <prompt> --plugin-dir <toy> --setting-sources project,local --strict-mcp-config --model haiku --permission-mode <default|auto> --permission-prompts none --output-format stream-json --verbose --include-hook-events`,
with a scrubbed environment (no `CLAUDE_CODE_*`, no user settings, plugins or hooks). Every result rests on the hook logs, the files on disk and the `tool_result` blocks, never on what the model said. `claude -p` starts in Manual (`default`) mode, so a permission prompt that nobody answers is a denial.

## Plan impact

Section tags in brackets refer to the design plan; drop them if the plan is not published.

1. **`Agent(...)` lists in agent frontmatter do not restrict spawning** (check 2). A master can start any agent type, built-ins and other plugins' agents included. The PreToolUse guard on `Agent` must compare `tool_input.subagent_type` with the master's own workers and deny the rest; the frontmatter entry only makes the tool available, so docs and tests must not call it a restriction. A second layer exists but is only a deny list: `permissions.deny` rules `Agent(ojtoy:other)` and `Agent(Explore)` (passed with `--settings`) blocked a forked-skill master's spawns ("denied by permission rule"), while the unlisted `ojtoy:child` started. Setup should write `Agent(general-purpose)` and `Agent(fork)` there, as the private setup does. [§3, §6, §7]
2. **`SubagentHandback` exists only in auto mode** (check 6). Without auto mode (`claude -p`, and any Manual-mode session) workers report plain final text, which only `SubagentStop.last_assistant_message` carries. `handback` and `capture` are two equal paths into one report processor: tests must cover both, and `capture` must cope with a null `last_assistant_message` (auto). The "no permission needed" row of the hook table is true in auto mode only. Per the docs, interactive terminal sessions start in auto mode on 2.1.283+ when the model is supported, while `claude -p` starts in Manual. [§3, §6, §13]
3. **The hook `allow` is load-bearing in Manual mode** (check 4). In auto mode the classifier approved the same benign calls with or without the hook, but the classifier gives no guarantee for riskier commands (not tested), so keep the guard's allow. Per the docs, deny and ask rules still beat a hook allow, and a hook allow has no effect in plan mode. A `PermissionRequest` hook shows "would have prompted", which is useful in tests. [§6]
4. **The data directory depends on how the plugin is loaded** (check 9): `ohmyjob-inline` with `--plugin-dir`, `ohmyjob-<marketplace>` when installed. `CLAUDE_PLUGIN_DATA` is not in the Bash env, so `bin/ohmyjob` can only learn it from `.ohmyjob/env.sh`. Setup must rewrite `OHMYJOB_DATA` in `env.sh` on every run (from the substituted skill text), and a developer who switches between `--plugin-dir` and an installed copy must re-run setup. Never hard-code the path. [§3, §5.4, §6]
5. **Start Claude in the workspace root** (extra D). Project settings are read only from the directory Claude starts in (tested with a project `env` value, in a git repo too; plugin enablement and `permissions.deny` live in the same file, so they follow). From a subfolder none of them apply, and with a user-scope install the gate `$CLAUDE_PROJECT_DIR/ohmyjob.json` in `hook.sh` fails open, which switches off the never-submit hooks. Make `hook.sh` walk up to `ohmyjob.json` as `find_root()` does, and say "start Claude in the workspace root" in the README and in setup. [§6 step 1, §10]
6. **Use `updatedToolOutput`** (check 7). Both fields work from a plugin hook; the schema calls `updatedMCPToolOutput` MCP-only and says to prefer `updatedToolOutput`. The §13 risk row can be downgraded. [§13]
7. **`claude plugin validate --strict` is a hard gate** (extra B). The validator reads `hooks.json`. At run time one invalid hook entry (tested: a bad `onFailure` on one PreToolUse entry) stops the whole plugin from loading: no skills, no agents, no hooks, only a `plugin_errors` entry in the init event, and the session carries on without the guard. Strict mode also fails on a missing `author` in `plugin.json`. [§9 P4, §11]
8. **`marketplace add` defaults to user scope** (extra E). Step 1 of the install in §10 changes `~/.claude/settings.json`. Use `--scope project` (listed in `--help`, not run here) to keep the workspace self-contained. [§10, §3.3]
9. **A master must keep its turn alive** (observation). A forked-skill master that ends its turn after launching background workers stops at once, and the workers' results go to the main session. The `next` long-poll loop of the prep and apply masters is what keeps them running: keep it. The main `Stop` hook fires once per turn (2 to 3 times in a run), so `report` must stay idempotent. [§6 `report`, §7]
10. **Confirmed, no change:** plugin agents ignore `permissionMode` (A); scoped names and anchored matchers (3); `bin/` on PATH for foreground and background subagents (5); a fork skill with `background: false` waits under `-p` (1); the Skill-tool chain (C); the exact hooks JSON of §6 (B); local and project scope installs load under `--setting-sources project,local` (8).
