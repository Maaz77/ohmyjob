Claude Code plugin · version 0.2.0 · MIT licence

ohmyjob

Runs a job search up to the last click. It searches job boards, drops postings that do not fit, writes a tailored resume PDF for every real match (or reuses a ready-made one the candidate supplied) and fills each application in the candidate's own Chrome. It stops before the final button. The candidate presses every Submit.

Overview

How a round works

Work happens in rounds. Each stage is one command, and the candidate checks the result before starting the next. Two optional loops feed what was learned back into earlier stages.

  1. Stage 1Find/ohmyjob:find-jobsScript, no AI model callsFound
  2. Stage 2Screen & tailor/ohmyjob:prep-jobsHaiku screens, Sonnet tailors, LuaLaTeX buildsSkipped-LowFitResume Built
  3. Stage 3Fill/ohmyjob:apply-jobsOne Haiku worker per Chrome tabPending ReviewNeeds Attention
  4. The candidateReview & submitUnblocks tabs, then /ohmyjob:continue-applying. Reviews each parked form and presses Submit. Moves back or deletes folders of jobs not sent.
  5. Stage 4Reconcile/ohmyjob:reconcileScript, no AI model callsSubmittedDeleted
Loop 1 · Retrospective /ohmyjob:retro
The candidate's verdict on skipped jobs becomes edits of the Fit Preferences that stage 2 screens against.
Loop 2 · Dream /ohmyjob:dream
Traces of past application runs become per-site notes that stage 3 workers read when they reach that site.

Three layers

Agents decide

Claude subagents judge and act. A master runs one stage and starts one worker per job (or per site). Each worker reads one brief and returns one JSON report.

Scripts keep the books

Deterministic Python behind one command, ohmyjob: queues, briefs, report checks, job notes, folder moves, tracker rows, cost. Agents never write the tracker themselves.

Hooks enforce

Run on every Chrome, file, shell and agent-start call in the job-search folder, whoever makes it, and cannot be skipped by a model. They allow, refuse or rewrite a call, and record what the scripts need.

Job status life cycle

The tracker refuses any other move between its nine statuses. The prep-start checks (closed, duplicate, no folder) apply to Matched rows too, and prep start gives a job folder without a row a new Found row. Reconcile marks any open row Submitted whose folder sits in Submitted/, Pending-Review/ or Needs-Attention/. In prep, a worker that sends no report leaves its job where it was; in apply, its job goes to Needs Attention. undo-find-jobs removes a day's rows that are still Found or Deleted.

Platform

Shared foundation

What every subsystem stands on: setup, the workspace folder, the tracker spreadsheet, the hooks, the mock-data guard and cost accounting.

/ohmyjob:setup/ohmyjob:help/ohmyjob:usage

Requirements

  • macOS or Linux. Windows is not supported (the scripts are bash-only), and WSL cannot drive the browser.
  • Claude Code 2.1.306 or newer (setup refuses older).
  • A direct Anthropic plan (Pro, Max, Team or Enterprise). An API key turns Claude in Chrome off.
  • Chrome, Edge or Brave with Claude in Chrome, plus the bundled helper extension. Only stage 3 needs a browser.
  • Recommended start: claude --model claude-haiku-5-5 --setting-sources project,local --strict-mcp-config --chrome in the job-search folder. Hooks load only from the folder Claude starts in.

Setup

  • Safe to run again: never overwrites a user file and never writes real user data. New files hold a mock persona, "Alex Example".
  • Checks the Claude Code version, the plugin scope and Chrome (a Chrome failure is only a warning). Asks before installing anything.
  • Installs into the plugin's own data folder only: virtualenv, uv's own Python, uv if missing, TinyTeX if no system LuaLaTeX builds the template, font caches and the extension. Nothing goes on PATH, in ~/.local or in ~/.cache.
  • Merges .claude/settings.json: allows Bash(ohmyjob *), denies the Chrome JavaScript tool, raises the subagent cap to at least 50, turns auto-memory and claude.ai connectors off. The user's own values win, except two numeric minimums, and the allow and deny entries are added to the user's lists.

Workspace

  • ohmyjob.json: search settings. Unknown keys and bad values are refused, naming the key.
  • Profile.md: Fit Preferences (three fields), the master Resume, numbered Follow Up Questions, optional Work Authorization (one line per country) and Languages.
  • Default_Resume_Files/: one yaml plus PDF per role, or ready-made PDFs.
  • One folder per job, moving Applications/ → Pending-Review/ or Needs-Attention/ → Submitted/. Each holds job.md, the tailored yaml and the PDF.
  • ats/ site notes, Worker_Limits.json, Dream_Report.md and .ohmyjob/ (run state, traces, logs, backups).

Tracker

  • Job_Tracker.xlsx, one row per job: Job URL, Status, Company, Job Title, Date Found, Location, Source, Match Score, Notes.
  • Atomic save. Refused while Excel or LibreOffice has the file open, or if the file changed on disk since it was loaded. Nothing is half-written.
  • Cells are stored as text, so a scraped =… never becomes a formula.
  • Enforces the status life cycle above.

Hooks

  • Five hooks: guard before Chrome, Read, Edit, Write, Bash and Agent calls; handback and capture check a worker's report; snapshot saves each page a Chrome call returns; report prints the run's cost report once.
  • Identifies the caller only from the call's parsed agent type, tool name and folder, never from text the model wrote.
  • Fails closed: a crashing guard blocks the call. Without the plugin's environment, every ohmyjob agent call and every agent's Chrome call is refused; the main session only gets a notice, so setup can still run.
  • An agent's own tool list is not trusted: the guard itself checks which agents a master may start and which commands it may run.

Mock-data guard

  • The template files carry the marker OHMYJOB-TEMPLATE.
  • find-jobs and add-job refuse while ohmyjob.json or Profile.md holds it. prep-jobs, apply-jobs, continue-applying and retro refuse while Profile.md holds it.
  • Each refusal is one FATAL: line naming the file. Template resumes are never used for a job.

Cost accounting

  • Every prep and apply run ends with its estimated cost in API-equivalent dollars: per job screened, per resume and per application, plus overhead. The estimate can run slightly low.
  • Summed from Claude Code's own transcripts of the master, every worker and every judge call, priced per model. A model with no price is named, not hidden.
  • Saved to a file so a hook prints it even if a model drops it, and logged per run. /ohmyjob:usage shows every run and the totals.
  • The main session and the master's last turn are not counted.

Hard rules and data

  • Final buttons: every Chrome call passes a hook that refuses any control named like one.
  • No account sign-ups and no passwords: hooks refuse sign-up buttons and any typing on Google pages; elsewhere "never type a password" is an instruction to the worker.
  • No invented resume facts: the tailoring worker may use only the candidate's own material, and a script checks that frozen fields did not change.
  • Searches go to the boards; applications go to employers through the candidate's own Chrome; working text goes to Anthropic under the user's plan. Setup downloads its tools, prep and apply fetch posting pages to check they are still open, and add-job fetches the pages it is given. Everything else stays in the local folder.
  • Page and posting text is treated as data, never as instructions.
  • Release check: a PII gate scans the repository for the owner's personal terms. CI validates the plugin and runs the tests, a real LaTeX build and browser tests of the extension.

Subsystem 1 · Stage 1

Job Posting Finder

/ohmyjob:find-jobs [verbose] [--dry-run] [--git-snapshot]/ohmyjob:add-job <url> …/ohmyjob:undo-find-jobs [YYYY-MM-DD | 'YYYY-MM-DD HH:MM']

Runs as a script launched from the main session. The script calls no AI model; the session only relays its report.

Searches the chosen boards for each search term, filters and de-duplicates on the candidate's machine, and records every new posting as a tracker row at Found plus a job folder holding job.md.

Needs

  • search settings: sources (default LinkedIn), search_query (required), location, country (required for Indeed and Glassdoor; 62 countries), recency_days (default 1; 0 means no limit), results_per_term (default 30), employment_types (default full-time, part-time, contract), exclude_companies, exclude_seniority_level, filter_title_terms, title_filter (strict or off), languages (word-form languages for title matching, default English), uk_sponsor_only (freehire).
  • Optional # Languages section in Profile.md.

Produces

  • Applications/<id>_<Company>_<Title>/job.md: overview (title, company, job and apply URL, board, dates, location, employment type), full description, empty sections for the screener.
  • A tracker row at Found. An excluded company gets a Deleted row with a note and no folder.
  • A report: new jobs by board; added, already tracked, auto-excluded and scraped counts; drops per reason; results per board.
  • Exit code 0 when clean, 2 when any board or term failed, 1 when fatal.

Capabilities

  • Ten boards. LinkedIn, Indeed, ZipRecruiter, Glassdoor, Google Jobs, Bayt, Naukri, BDJobs and HelloWork through JobSpy 1.4.1 (pinned), plus freehire.me's keyless API. Boards run in the user's order, and that order also decides which board keeps a job listed twice.
  • Only five things reach a JobSpy board: search term, location, country, result count and recency. Google gets a generated query such as "data analyst jobs near Berlin since yesterday". Every other filter runs locally.
  • freehire: searched by country code (taken from location, else country; skipped with a warning when neither names one) with a title-phrase query, in pages of 100 up to 10,000 results. Recency and the exclusion of aggregator feeds (Adzuna, Jobleads, WhatJobs) run on the server. Optional UK licensed-sponsor filter. One retry on rate limits and server errors, honouring Retry-After up to 30 s. Warns when the API ignores a filter, and on zero results reports the 7-day, 30-day and all-time counts to explain why.
  • LinkedIn pacing: a random 1.0–2.5 s pause before every detail page. When more than half of a board's detail pages fail (and at least 3), the report says to search less.
  • Failure isolation per search term: a failing term or board is reported as ERROR and the rest still run. A failing search ends the run only when every board failed and nothing came back.
  • One job id everywhere: a LinkedIn job keeps its numeric id. Any other address becomes "9" plus 14 digits hashed from host, path and query. Tracking parameters are stripped when a posting is collected: utm_* plus 22 named ones such as gclid and fbclid (LinkedIn addresses lose 8 more). The finder, the folders and reconcile all use this rule.
  • Title matching (strict): every word of a search term must meet a title word by accent-folded form or dictionary word form, in any order, with built-in aliases (Sr. = senior, ops = operations, developer → engineer). With off, every title passes but the other filters still run.
  • Run options: verbose streams board, term and filter events live. --dry-run searches but writes nothing. --git-snapshot commits the tracker and Applications/ first (skipped outside a git repository or when .gitignore excludes them).
  • Unattended runs: runs in the background and asks nothing, so it also works from a scheduled claude -p.
  • Add by hand: add-job fetches each address with Python's standard library (no Chrome, no JavaScript; 20 s and 3 MB caps), reads the page's schema.org JobPosting data, and writes the same folder and Found row with Source "Added by hand (site)". Search filters do not apply. An excluded company only gets a warning.
  • Undo: undo-find-jobs removes the rows of the newest Date Found day (add-job rows included), or of a date or minute given, that are still Found or Deleted, plus their Applications/ folders. It shows a dry run, asks, copies the tracker to .ohmyjob/backup/, and applies only with the plan digest of that dry run.

Limits

  • Only the ten boards. Career pages come in through add-job, which cannot render JavaScript or log in; a page that answers with a sign-in redirect or wall, as LinkedIn job pages often do, is refused.
  • results_per_term counts before local filtering, so a strict filter can leave few jobs from many results.
  • freehire is searched by country only (the city is never sent or checked), ignores results_per_term, stops at 10,000 results per term and always drops internships.
  • The posting-language filter covers freehire labels only, and a label names the language an ad is written in, not the language the job needs. Stage 2 judges the rest.
  • Junk patterns are English. Vague or thin postings are left to the screener.
  • Title matching needs scripts with spaces between words (no segmentation for Chinese or Japanese). The software-flavoured aliases cannot be switched off.
  • exclude_companies is fuzzy and can over-match short names: "Meta" also matches "Metal".
  • Within one board, reposts under different ids are caught only when title, company and city match exactly.
  • LinkedIn pages that fail to load are not retried within the same run.
  • Undo knows a run only by its Date Found prefix, removes every same-date Deleted row, and cannot restore deleted folders.

Subsystem 2 · Stage 2

Screening & Resume Tailoring

/ohmyjob:prep-jobs [job-id …]/ohmyjob:build-resumes [file.yaml]/ohmyjob:build-job-resumes <names>/ohmyjob:master-resume/ohmyjob:edit-template <request>

Runs as a forked Haiku prep-master, Haiku screen-workers and Sonnet resume-workers, with scripts and LuaLaTeX.

Scores every Found job against the candidate's own profile, drops weak or impossible matches with the reason written to the tracker, and builds a tailored PDF with the exact page count for each match. Screening and tailoring share one queue: a match starts its resume worker while other jobs are still being screened.

Needs

  • A filled-in Profile.md without the template marker. The screener leans on its Fit Preferences (Seniority / experience level, What I'm looking for, Dealbreakers), Resume and Follow Up Questions; Work Authorization and Languages are optional.
  • At least one usable resume in Default_Resume_Files/: a role yaml with its built PDF (tailorable) or a PDF alone (ready-made). Template files and PDFs of the mock persona are never used.

Produces

  • Skipped-LowFit with the reason in Notes (folder deleted), or Matched, then Resume Built, Resume Failed or Deleted.
  • In each kept folder: <First>_<Company>_<Title>.yaml and .pdf (name cut at 50 characters), and notes in job.md on what changed and why, the gaps the material could not cover, and what was cut to fit.
  • An end report: closed, duplicate and refused jobs listed one by one, low-fit skips counted, work-authorization and language block counts, and the API-equivalent cost per job screened and per resume.

Before any model runs

  • Row and folder pairing by job id, for Found and Matched rows: a row without a folder becomes Deleted; a fresh folder without a row gets a Found row. A folder that already holds resume files, or shares its id with another folder, is left alone and reported.
  • Duplicate postings (same company and title): keeps the one already at Resume Built, else the one with a stated location, else the lower id. The rest become Deleted.
  • Closed-posting check (no model, no Chrome): drops a posting only on positive evidence: LinkedIn's "No longer accepting applications", a Lever 404, a Greenhouse error redirect, or HTTP 410 elsewhere. Errors, timeouts, rate limits and sign-in walls count as open. One request at a time per site, 1–1.5 s apart, a site left alone for the rest of the check after 3 refusals in a row, 6 sites in parallel, a 40 s budget.
  • Work-authorization pre-pass: reads English and German postings for "no sponsorship", "right to work", "citizens only", "permanent residency" and named clearances. It takes the one country in the job's Location and compares it with the candidate's line for that country (citizen, then permanent resident, then authorized, then needs sponsorship; a country line beats the EU line). A named clearance blocks only when Profile.md says the candidate holds none. Only when both sides are explicit is the job skipped, with a "Work authorization block:" note quoting both, and no worker is started.
  • Resume catalog, built once per run: title, introduction, roles and skills of each role yaml, and the full text (up to 6,000 characters) of each ready-made PDF.

Screening (one Haiku worker per job)

  • Plays a strict senior recruiter in the candidate's field, judging the substance of the work rather than keywords, and scores 0–10. It is told not to inflate scores.
  • Its brief puts Fit Preferences first, then the whole Profile.md, the list of resumes and the posting; the worker reads the resume catalog file once.
  • Picks the single closest resume. A near tie between a role yaml and a ready-made PDF goes to the yaml, because only the yaml gets tailored.
  • Second net for work authorization: requirements the script cannot read (other languages, unusual wording, "must reside in X") are judged against the Work Authorization lines and the Follow Up answers.
  • Language rule: an explicit requirement, or a posting written entirely in a language the Languages list lacks, is a dealbreaker. The list is read as complete. There is no level test.

Tailoring (one Sonnet worker per match)

  • Starts from an exact copy of the matched yaml. Facts may come only from Profile.md and that yaml; nothing is invented, inferred, upgraded or borrowed from the posting.
  • May reorder, reword, merge or split bullets, pull in projects and skills from Profile.md, regroup skill rows, rewrite the summary, and retitle the headline to the posting's title.
  • Only title, introduction, experience, projects and skills may change. Numbers, dates, employers, degrees, credentials, past job titles, contact details, education and section order stay exact, and no rewording may promote a claim.
  • Content is cut only to hold the length. The PDF must match the source PDF's page count exactly. To fit, it tightens wording, then drops the least relevant bullets, then skill items, and only last a whole project. Font and margins never change.
  • A script checks every draft before compiling: same keys and roles; no added seniority word in the title; the introduction opens with the title and is no longer than the source; each role keeps 2–4 bullets unless its source had fewer or more; a changed bullet fits in 124 characters and a changed skill row in 109; no new repository that Profile.md lacks. A failed check does not use up one of the 4 builds.
  • May refuse a job before editing, on three grounds only: the deciding requirements have no support in the candidate's material, the job is another profession, or a dealbreaker applies. A missing tool, a missing industry or a higher title is never a reason.

Write order every time: job.md, then the tracker is saved, and only then are folders deleted. A crashed run is harmless: unrecorded jobs stay Found or Matched and the next run picks them up.

Resume tooling

  • Rendering: one complete yaml per resume, through a Jinja LaTeX template and the vendored Awesome-CV class, compiled by LuaLaTeX (no shell escape, 180 s limit) in a separate folder per build. A workspace copy of the template overrides the plugin's.
  • build-resumes: a PDF next to every role yaml (never Template*), OK or FAIL per file.
  • build-job-resumes: rebuilds a job's tailored yaml after a hand fix and sets the row back to Resume Built. More pages than the source fails.
  • master-resume: merges every role yaml (the same job, degree or award across files becomes one entry; bullets and skill items 90% or more similar keep the longer text) plus the text of ready-made PDFs into a draft Resume section. Claude adds the PDF facts. Applying replaces only that section, after a backup.
  • edit-template: restyles the resume or CV or adds a section from a plain-language request. It asks when resume or CV is unclear and edits only the workspace copy. When it adds a section, it also adds sample lines to the two template yamls. It always builds both samples to prove they compile; after three failed builds, or when no fix is clear, it resets the copy.

Guard rules for prep agents

  • A worker's first call must read its own brief.
  • A screen worker can read only its brief and the catalog.
  • A resume worker can read its brief, its yaml and its PDF, edit only its yaml, and run only the build of its own job.
  • The master can start only these two worker types and run only fixed ohmyjob prep commands.
  • After 17 minutes, every tool call of a worker is refused. Reports are checked and sent back at most twice.

Limits

  • The work-authorization script reads English and German only, never decides when the job's country is unclear (remote, several countries, a bare city) and never compares clearance levels.
  • Apart from the finder's label-based drop of freehire postings, language requirements are judged only by the Haiku screener, with 8 turns per job. The resume worker treats the screener's notes as a fast first read and reads the posting again.
  • The closed-posting check has evidence rules only for LinkedIn, Lever, Greenhouse and HTTP 410.
  • Duplicate detection ignores location: the same company and title in two cities count as one job.
  • Ready-made PDFs are never tailored.
  • Tailoring cannot add roles or change employers, titles, dates, education, contact details or section order, and can refuse only before editing.
  • Text the resume fonts cannot draw (the code names Chinese, Japanese, Korean and Arabic) fails the build.
  • Resume Failed jobs wait for a hand fix and /ohmyjob:build-job-resumes.

Subsystem 3 · Stage 3

Application Browser Agent

/ohmyjob:apply-jobs [--selected "<names>" | --top-k-match N]/ohmyjob:continue-applying

Runs as a forked Haiku application-master, one Haiku application-worker per job (with a one-time Sonnet takeover), judge calls, the hooks and a helper Chrome extension.

Opens one tab per job in the candidate's own Chrome, fills each application from Profile.md and the tailored resume, uploads that job's PDF and stops before the final button. Blocked jobs wait in a Chrome tab group for the candidate, then continue where they stopped.

Needs

  • Rows at Resume Built, each with exactly one tracker row, one folder, job.md, a PDF and a job URL. Others are listed as skipped.
  • Chrome, Edge or Brave with Claude in Chrome and the helper extension. Without the helper the run only warns, and Google sign-in pop-ups end in Needs Attention.
  • LinkedIn signed in when any job is on LinkedIn. Google signed in, for "Continue with Google".

Produces

  • Pending Review (folder to Pending-Review/), Needs Attention (folder to Needs-Attention/, tab kept in the "Needs Attention" group) or Deleted (posting closed).
  • A note per job: where it stopped, the final button left for the candidate, filled fields, the uploaded resume, drafted answers to check, consent boxes ticked, open items.
  • The forms' questions, asked once at the end. Answers are saved to Profile.md.
  • Cost per application, a ledger line per job and, for informative runs, a redacted trace for Dream.

Run sequence

  1. Work-authorization gaps. Before the run, the main session asks for the candidate's status in each job country Profile.md does not cover (citizen, permanent resident, authorized, needs sponsorship) and saves the answers.
  2. Queue. All Resume Built rows, or --selected folder names (each must match exactly one folder), or the --top-k-match N best Match Scores; not both. The closed-posting check drops closed jobs before any tab opens.
  3. Preflight. LinkedIn sign-in (a login, authwall or checkpoint page stops the run), the helper's version, a self-test of the button judge (the Italian "Invia candidatura" must be refused) and the watchdog limits.
  4. Tabs and briefs. One tab and one brief per job: Profile.md without Fit Preferences, the posting, the tailored resume's title and introduction, the PDF path, and the site notes to read on arrival.
  5. Workers start in free slots (49 by default). First page loads are spaced 4 s apart, so one account is not hit by many tabs at once.
  6. Finish. Every report is checked, and a Sonnet check reviews the filled values of each parked form. Notes are written, folders moved and the tracker saved once. Tabs move into the "Pending Review", "Needs Attention" and "Deleted" groups; stray tabs close and job tabs stay open.
  7. End. Cost report, ledger and traces, usage log. The run folder is deleted.

How a worker fills a form

  • Answers only from its brief, and splits stated facts instead of asking: country, city and postcode from the address; first and last name; the dialling code from the phone.
  • Keeps values LinkedIn prefilled. Work-authorization and sponsorship answers follow the country's status line (an EU line covers EU countries) or a Follow Up answer that names the country.
  • Gives every other question the most plausible answer and lists it under "Drafted answers" for review. Open-text answers are 3–5 sentences, at most 120 words, in the question's language. "How did you hear" gets LinkedIn for LinkedIn jobs, otherwise "Job board" or the nearest option; voluntary diversity questions get "Prefer not to say".
  • Stops only for a required question about legal status (work authorization for an uncovered country, citizenship, clearance, criminal record) or a number or credential (years with a skill, degree, licence, certificate, grade, salary) that Profile.md does not answer. It fills every other field on the page first, then reports the questions word for word. Optional ones stay empty and are listed.
  • Never judges fit and never stops because a posting says nothing about sponsorship. Fit was decided in stage 2.
  • Ticks consent and declaration boxes and lists them for the candidate. Picks the most private cookie choice.
  • Signs in with "Continue with Google" where offered, choosing the account with the profile's email when listed, otherwise the only or first signed-in account. Allows basic-profile consent only and never types on Google pages.
  • Uploads only that job's PDF, through the page's file input, never through a system dialog.
  • Handles one-page forms, multi-step dialogs (LinkedIn Easy Apply, Workday), Apply links to company sites, applications that open in a new tab, forms inside frames from another site, error pages (up to 2 reloads), closed postings and "already applied" pages.
  • Saves tokens: reads pages through the interactive filter, fills a whole page in one batch, takes screenshots only when needed.

Recovery

  • Sonnet takeover, once per job, on the same tab, from the open page: when a Haiku worker stalls, repeats the same refused step, goes idle, ends without a report, runs out of budget, stops before any final control, or reports an account wall that no page of the tab showed (a password field or a one-time-code field seen on any page counts). Not for questions, closed or submitted jobs, fill reviews, real account walls or unclassified blocks.
  • Upload-hang retry: a browser alert after an upload (often a too-long file name, shown to the worker as a banner) renames the resume to a short <First>_<Company>.pdf, never over an existing file, and restarts the job once.
  • Progress watchdog (Worker_Limits.json, read live, unusable values fall back to defaults): progress means a new page, a first fill, a first choice, an upload or a Google step. A nudge after 15 calls without progress, a stop at 25; a stop after the same refusal 5 times in a row; at most 150 calls; a worker idle for 6 minutes loses its slot, and a late report still counts.
  • Sign-in lease: only one tab signs in to a given site with Google at a time. Others wait 15 s and reload; a stale lease expires after 90 s.
  • Lost workers: a worker that ended without a report frees its slot at once; one printed but never started is issued again after 60 s.

Follow-up questions

  • Collected across all jobs and de-duplicated. Questions Profile.md already answers are dropped.
  • Asked once, after the run, in one message, each with the jobs that asked it. The text is treated as untrusted page content.
  • Answers are appended as numbered lines under Follow Up Questions, so later runs answer them alone. Jobs with every question answered are listed as ready to continue. Skipped questions are dropped at reconcile.

Continue applying

  • Takes every tab in the Chrome group "Needs Attention", including tabs the candidate put there, and loads the current helper script into tabs opened before an extension reload.
  • Tries the tab id from the last note first, but only if that tab still shows a site the job used. Other tabs are matched by the page shown (last noted address, Apply and Job URL, shared path, company in the tab title); only mutual best matches count and ties go to neither, so a Chrome restart that renumbers tabs does no harm.
  • Each worker continues from the open page. The last run's note is history: a step the hook refused then is tried again.
  • A job without a tab is left for reconcile; a tab matching no job stays open in "Needs Attention"; a job whose last run saw a submission message is never continued.

Helper extension

  • Opens sign-in pop-ups as tabs inside the run's tab group, so the worker can drive them.
  • Names icon-only controls from their icon ("Continue with Google" for the Google logo, app-store badges and Google apps excluded), marks each name as a guess, and tags each job tab's title with its Google control count and the helper version.
  • Exposes any frame of 200×200 px or larger, from another site or the same one, as a link holding the frame's real address, kept current as it navigates or resizes; the worker opens a form frame as a page of its own. A frame with no address of its own gets a tag, so the worker reports it at once.
  • Marks form fields, because Claude in Chrome shows no field state: [x] ticked or selected, [req] required, [disabled], [invalid]; a text field reads "Label = value" and a radio "Question / Option". Buttons and links keep their own live names.
  • Answers page dialogs in run tabs: an alert becomes a banner the worker can read, confirm and prompt are answered Cancel (never OK), and "Leave site?" prompts are dropped. When the tab leaves the run, the page gets its own dialogs back.
  • Groups finished tabs into "Pending Review", "Needs Attention" and "Deleted", and for continue mode moves every "Needs Attention" tab back into the run.
  • Apart from that continue-mode pull, changes only tabs in the run's group. Its scripts load on every page but stay inactive elsewhere, and it accepts group commands only from the run's own home tab.

Site knowledge

  • Ships notes for Greenhouse, LinkedIn Easy Apply, Phenom and Workday. Dream adds notes for other sites, and a workspace note replaces the plugin note of the same name.
  • Built-in shortcuts: a Greenhouse form embedded in a company page opens at its direct form address; LinkedIn's safety redirect is rewritten to the company address.

Limits

  • Refuses final buttons by word lists in 62 languages; for names no list knows, application workers ask the Haiku check, and a failed check means no click. A parked form is not a sent application.
  • Never creates an account with a password and never types a password. Sites that demand one end in Needs Attention for the candidate to sign in.
  • CAPTCHAs, bot checks and extra Google permissions (Drive, Gmail, Calendar, contacts) stop the job.
  • LinkedIn must already be signed in. The check reads the page address, not the account.
  • Forms inside frames (from any site, the same one included) work only through the helper's frame link; a frame with no address of its own cannot be opened.
  • A sign-in button inside a small frame from another site (a social-login widget) and forms built from shadow DOM components (SmartRecruiters Easy Apply) cannot be read by Claude in Chrome; the worker stops with a code and the job goes to Needs Attention.
  • Required legal-status and credential questions that Profile.md does not answer stop the job until the candidate answers; optional ones are left empty and listed.
  • Outside the pipeline (the main session or another agent driving Chrome), the guard applies only the core rules: the word lists on a control's own name, the nameless-submit and Apply rules, fresh references and the safe-key list. Consent, Google, sign-up and judge rules apply to application workers only.
  • Passwords are blocked by a hook only on Google pages and through the sign-up refusal; on other sites "never type a password" is an instruction to the worker.
  • A cookie banner whose only way past is "Accept all" stops the job.
  • At most 49 workers at once by default. One run at a time: a new run clears the last run's state.

Subsystem 4 · Stage 4

Reconcile

/ohmyjob:reconcile

Runs as a script launched from the main session. The script calls no AI model; the session only relays its report.

Closes the round. Brings the tracker in line with where each job's folder now sits, archives sent jobs in Submitted/, and clears what should not carry over to the next round.

Flow

  1. Shows the caveat below and waits for a clear yes that the folders are tidy.
  2. Dry run: every row that would change with old and new status and folder move, unmatched folders, the number of questions to drop, the backups to delete and a plan digest.
  3. Asks to confirm, then applies bound to that digest. A changed plan is refused and shown again.

Decision rules (open rows: Found, Matched, Resume Built, Resume Failed, Pending Review, Needs Attention)

The job's folder is inRow becomesFolder
Pending-Review/ or Needs-Attention/SubmittedMoved to Submitted/
Submitted/ (the candidate applied by hand and moved it there)SubmittedStays
Applications/unchangedUntouched
Nowhere (the candidate deleted it)Deleted—
  • A Submitted row whose folder is still in a review folder only gets the folder moved. Deleted, Skipped-LowFit, Submitted and hand-typed statuses are never rewritten.
  • A folder whose id matches no row, an id shared by several rows, or one job with folders in two places is left untouched and reported. Each duplicate open row gets a note with the status of the oldest row sharing its id. Folders without a leading id are ignored.
  • Invariant: Submitted rows must equal folders in Submitted/ after the plan, or nothing is written.
  • The tracker is saved once, before any folder moves; a move that fails is healed by the next run. A destination that already exists stops the run before any write.
  • On success it deletes the unanswered follow-up questions and the tracker backups of undo-find-jobs.
  • Exit codes: 0 clean; 1 some folders unresolved, the rest applied; 2 invariant failed, nothing written; 3 fatal.

Limits

  • Cannot know whether a form was really submitted: any folder in Pending-Review/ or Needs-Attention/ counts as sent. The candidate must move unsent folders back to Applications/ or delete them first.
  • A job applied to entirely by hand stays open until its folder is moved to Submitted/.
  • Never touches Applications/ and does not clean up unresolved folders.
  • Unanswered questions are gone for good. A job that runs again asks again.

Subsystem 5 · Loop on stage 2

Retrospective

/ohmyjob:retroohmyjob retro reject

Runs as a conversation in the main session. During retro, a script is the only writer of Profile.md. No agent.

Closes the loop on screening. The candidate marks skipped jobs that should have matched and types standing preferences; the session drafts edits of the three Fit Preferences fields; each edit is accepted or refused one at a time, and the last pass can be undone.

Flow

  1. Review. Lists unreviewed Skipped-LowFit jobs, newest first, 15 at a time: company, title, link, score and the screener's last note, shown as data. Junk skips are left out. Only answered skips count as reviewed, stored by job id so re-sorted or deleted rows keep their marks.
  2. Own words. Standing preferences ("stop matching consulting roles") are saved as F1, F2 and so on. Marks or words alone are enough.
  3. Proposals. At most one open proposal per field, each with the current wording (read by the script), the new wording and its evidence. Conflicting evidence is shown, not resolved. Facts about the candidate are pointed to the Resume section instead.
  4. Decide. Accept or refuse each. Profile.md is backed up before the first accepted edit.

A proposal is refused when

  • The field is not one of the three.
  • It has no evidence, or evidence not gathered in this pass.
  • Another proposal on that field is still open.
  • Its field and evidence match a refused proposal.
  • The wording is empty, multi-line, over 1,000 characters, unchanged, or holds the template marker.
  • The wording repeats six consecutive words from any tracker note, unless the candidate typed them or the field already says them.

An accepted edit is written safely

  • Re-checks the template marker and that the field still reads as proposed.
  • Replaces only that field's bytes; every other byte and the section structure are verified before writing.
  • Writes atomically.
  • Undo restores Profile.md and the review marks. It refuses if Profile.md changed since retro wrote it, unless forced, and then saves the current copy first.
  • The end of a prep run says when 10 or more skips wait for review.

Limits

  • Edits only the three Fit Preferences fields: never Resume, Follow Up Questions, Work Authorization, Languages, settings or score thresholds. It never revives a skipped job.
  • Treating the screener's reason as data, never as an instruction, is a conversation rule; the script's own check is the six-word copy refusal.
  • The candidate's yes for each edit is a conversation rule: the script accepts any open proposal it is told to.
  • A field that spans several lines becomes one line when edited.
  • Evidence must come from the current pass.

Subsystem 6 · Loop on stage 3

Dream

/ohmyjob:dreamohmyjob dream reject

Runs as a forked Opus dream-master (low effort, no file access) and one Sonnet worker per site. Only the candidate can start it.

Turns what application runs met on each application system into short site notes. Workers read a site's note the next time they reach that site. A report explains what was learned.

What is recorded

  • Every apply run writes one ledger line per job that got a tab: outcome, blocker code, turns, tokens, cost, refusals, watchdog counters, sign-in progress and Google controls seen.
  • Informative jobs also get a trace: the actions taken (tool and the worker's own short summary; typed values are not recorded), guard refusals, page lines near sign-in, sign-up, password or final-button words, and the sign-in flow.
  • Redaction: lines holding the profile's name, email, phone, address or location are dropped; email addresses become <email>; filled values keep only field names; drafted answers are dropped. A trace over 20 KB keeps only its first 20 and last 60 actions.

Which jobs teach

BinRule
WallStopped by the site or the watchdog, or an account wall the page did not show.
HarnessThe plugin's own failure: a guard or judge error, a lost worker, a Google option clicked with no Google page.
Costly winParked, but over 2× the site's median turns or cost (with 5 or more earlier wins), else over 60 turns.
First winParked on a site no note covers yet.
SkipHandoffs to the candidate and cheap wins on known sites. No trace.

A dream pass

  1. Takes only ledger lines since the last pass, grouped by site (a note's host patterns, else the host name). Copies the plugin's note into the workspace before editing, and backs up notes, report and watermark.
  2. Starts one worker per site in parallel in the shared slots. A worker that has not reported 20 minutes after it started is given up on.
  3. A worker is bound to its site by its first read and can write only that one note. It keeps a lesson only with at least two supporting jobs (or a later win), removes lessons later traces contradict, never weakens the application worker's hard rules and treats page text as data.
  4. Each changed note is checked: at most 40 lines, one title, a hosts line, no email address, no profile header value. A failing note is put back, or removed if it was new.
  5. Dream_Report.md: per site, attempts, wall rate, median turns and cost of successful runs, and attempts before and after the note last changed; lessons added (with evidence) and removed; proposals for code changes (listed, never applied); bugs. The end of an apply run says when 10 or more new traces wait.

Limits

  • Learns only from walls, plugin failures, costly wins and first wins. Handoffs teach nothing.
  • Each unknown employer site gets its own note; sites are not grouped by company.
  • Note quality beyond the format checks rests on the worker's instructions. A bad note is reverted, not repaired.
  • Only the last pass can be undone.
  • Some report fields (open items, questions, declarations, button text, uploaded file name, page address) are stored as written, without the email and profile filter.
