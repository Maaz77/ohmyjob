# Safety

How ohmyjob keeps you in control of every application. [Back to the README](../README.md)

- **Never submit.** Hooks run on every Chrome call — in the main session and in every ohmyjob agent — and refuse final controls: Submit, Send, Confirm, Finish and their equivalents in many languages, plus unnamed submit buttons. `javascript_tool` is denied in the workspace settings. The rules differ by caller:
  - **Application workers** may act only in their own tab and its sign-in tab; every click carries an action note, and a click whose note says it sends the application is refused; uploads are limited to that job's own folder (its resume, or one other file already in that folder); and a button name that no word list can decide goes to a short extra check, which refuses the click if it fails, unless the name carries none of the dangerous words (see the last bullet of this list).
  - **The main session and any other agent** may click only on references from a fresh read of that tab, one pressable click per read, with no coordinate clicks, only allowlisted keys (Tab, Shift+Tab, Escape, Backspace, Delete, arrows, Home, End, Page keys, Ctrl/Cmd with A, C, V, X, Z, Y: so no Enter, Return or Space), navigation to http(s) addresses only, no Apply click on a job board or under a filled form, and the control's own name checked against the final word lists (in 62 languages). The consent, Google, OAuth, sign-up and delete rules and the extra check apply to application workers only. The delete rule has two word lists, and both read a control's own name plus the text of the elements inside it (so a button named "Options" over a child "Remove education" counts). A withdraw word (Withdraw, Zurückziehen, 撤回 ...) is refused outright, with no model call, because withdrawing an application cannot be undone; a word whose "remove this row" sense is not confirmed sits in that list too, which is why every delete control on a Turkish or Albanian page is refused. A delete word (Delete, Remove, Löschen, Entfernen ...) is never allowed on its name alone. Two checks follow it. **First the structure:** if a text field, text area, combo box, search box, spinner or radio button sits in the same container as the control — or, on a page the browser shows with no structure at all, within two lines of it — the click removes an answer and is refused with no model call. This is why a form entry stays refused: the hook sees the labels around a control and never its field values, so it cannot tell a filled row from an empty one, and it does not ask. **Then the Haiku check**, which is told what encloses the control, not only what sits beside it: it allows the click only when the container that directly encloses it is itself the thing being removed and is something the agent added and can re-add (an upload or attachment area, a filter or tag list, a list of search chips), and blocks a form entry, the candidate's account, profile, saved data or a sent application, and a control with no container at all. The containers arrive separated and outermost first, so an upload area nested in a form named "Application form" still passes — that is the control that drops an uploaded file so a better resume can be attached. The check's rule is framed on what the click does rather than on the control's name, so "Clear", "Reset", "Discard" and a trash icon are judged the same way although no word list knows them; an X that only closes a dialog, a menu or a banner stays a Close and is allowed. A delete word inside a cookie or consent dialog is refused with no model call, and the verdict for a delete word is never cached by name.
- **One exception to the Apply rule.** On a tab that looks like a form but where the worker answered nothing (a job page with search boxes), a click on an Apply link that only opens the next page passes. All seven must hold: (1) an Apply word in the link's name or inside it; (2) the role is `link` with a navigable address (backslashes read as slashes, http or https only), and the note says it opens or loads a page or form (a note that says it submits is refused, and "Applies to this job" does not pass); (3) the tab has no fill, upload, tick or option of the worker (a toggle of a cookie dialog does not count); (4) the tab is not a `/continue-applying` tab, also not on the job's own address; (5) the target is another page (host and path, ignoring query, hash, case and a trailing slash); (6) neither the current page nor the target is a job board (the `BOARD_LABELS` list plus more boards used only here); (7) the page shows no file input. Buttons, `#` and `javascript:` links and every other tab keep the old refusal. When no answer was given, the refusal tells the worker to stop with `blocked`, or with `parked` only if the page is a form filled up to that button.

- **One exception for pickers and lists.** A control that carries a final word but sits inside a `listbox`, `menu`, `menubar`, `tree`, `treegrid`, `grid` or `combobox` closes that widget rather than sending a form: a date picker's "Done", a multi-select's "Confirm". Such a click skips the word refusal and goes to the short extra check instead, with the name of the widget it sits in as context; the check refuses it if it fails, and a failed check refuses it too, so no control is ever allowed on its name alone. `dialog` is deliberately not on that list, because the submit button of a LinkedIn Easy Apply dialog and of every modal application form sits inside one — so a picker that renders as a dialog stays refused. This applies to application workers only: a click of the main session or of any other agent is still refused on the word alone, because there is no extra check behind it to defer to.
- **Icon-only buttons.** `read_page` shows a button with no text and no label as nameless, and a nameless submit button is refused. The helper extension names such a button from its icon (an svg `<title>`, a sprite id, a `data-testid`, or a single non-framework class) and marks the name `[icon] `. It writes nothing on a control `read_page` can already name — one with a `title` attribute, or with an image that has an `alt` inside it — because the guessed name goes into `aria-label`, which outranks both, and the word the guard refuses on ("Delete" on a trash button) would be gone. A guessed name is evidence for the short extra check, never an allow: it gets no whole-name allow from `SAFE`, no Apply pass before a fill, and no allow from the consent pass. A final, Apply, consent or sign-up word in it sends the click to the check, which is told that the name was read off an icon, and the verdict is cached apart from the same name written by the site. A delete word in a guessed name is routed like any other delete word, not refused on the name: the container decides (a delete beside form fields is refused with no model call; otherwise the check allows it only when the container that directly encloses it is itself what the worker added and can re-add, such as an upload area). Only a withdraw word is refused outright. The other hard refusal: a button that declares `type="submit"` and has no name or only an icon name, because the page itself says it submits the form — the one exception is the extension's own Google name, exactly `Continue with Google`, which goes to the check. A button with no word in any source stays nameless and stays refused. Application workers only.
- **Five narrow loosenings, for application workers only.** Each keeps every other refusal as it was; the main session and any other agent keep the old rules with no exception (no Enter, no line break, no check to defer to).
  - **Enter in a search list.** Enter or Return, alone, is allowed only while the focused control is a `combobox` or a `searchbox` (a Workday "School or University" or "Skills" list commits on it; both labels count as search fields). A plain `textbox` stays refused, because Enter there submits a form. Space, Shift+Enter, Cmd+Enter and every other spelling stay refused.
  - **A second upload file.** `file_upload` still takes exactly one path per call. It may be the job's resume, or any one existing file whose resolved path sits directly in the same folder as that resume (the job's own folder, for example a cover letter). The path is resolved first (`~`, `..` and symlinks are followed) and its parent must equal the resume's parent, so no other directory is reachable. The call is rewritten to the resolved path.
  - **A line break in `type`.** `\n` is allowed in a `type` action only while the focused control is a multi-line text box: a `textarea`, or a `textbox` that carries `aria-multiline="true"`. When the box cannot be told to be multi-line it stays refused. A tab and every other control character stay refused everywhere.
  - **"Accept all" with nothing else on offer.** In a cookie or consent dialog an accept-all name is allowed only when the dialog offers no private choice and no toggle: the dialog is found around the control (a `dialog` or `alertdialog`, or a line with a cookie or consent-platform word in its name), and inside it there is no checkbox, radio button or switch, no other button or non-link control at all, and no link with a reject, decline, only-necessary, settings or manage word (`PRIVATE` and `CMP` in `lexicon.py`). It also needs a name the site wrote (not an icon guess), a tab that showed no form, and no delete or final word in the name. Any doubt, including a dialog that cannot be found, keeps the refusal. The allow is written to the run log as `consent-dialog` with `only_choice`.
  - **A failed Haiku check on an ordinary name.** When the check itself fails (no answer, a timeout, a malformed answer; never a "block"), the click is allowed only if the control's own name plus the text inside it carries none of the final, Apply, delete or withdraw, sign-in permission, consent or sign-up words, and the name is neither an icon guess nor a Google option. Any such word keeps the old refusal ("The Haiku check could not check ..."). The allow is not cached, so the next click asks again, and every one is written to the run log as `judge-fail-open`. The price: a final button named in a language or phrasing no word list knows is allowed while the check is down.
- **Google sign-in and Google apps.** A name with a Google word counts as a Google sign-in option only when it names none of Drive, Docs, Maps, Pay, Play, Photos, Sheets, Calendar, Meet or Cloud, so "Upload from Google Drive" is an ordinary button for the short extra check, takes no sign-in lease and is not counted as a missed sign-in in the report. An app name counts however it is written, beside the word or glued to it: `GoogleDrive`, `google_drive.svg` and `gdrive` are app names too, in the extension's icon test as in the guard's name test, and so is an app's mark in the four Google brand colours. The extension names an icon-only Google logo `[icon] Continue with Google`, so that one sign-in click costs a check as well (cached per host for the run); the sign-in lease is taken only after the check allows it, and nothing is written to the run log for a click the check refused.
- **A park is graded on the page, not on the report.** A worker that stops reports the final button it saw, but that is its own claim. The run counts the job as filled and waiting for you only when a final control is actually in the last snapshot of that tab, outside any picker. Otherwise the job goes to Needs Attention, where you look at it, instead of to Pending Review, where it would look finished.

- **Before setup, the guard cannot run.** Until setup has created the Python environment, the main session's Chrome guard lets a call through with a notice — but no pipeline can run before setup, and every agent's Chrome calls (not only ohmyjob agents) are denied outright. Run `/ohmyjob:setup` first.
- **Dialogs in run tabs.** In a run-group tab the helper extension answers `confirm` and `prompt` with Cancel (never OK), shows `alert` as text (`[AA alert] ...`) and drops `beforeunload` prompts, so no worker can accept a page's dialog. End-of-run grouping gives native dialogs back, so a `confirm` on your own Submit in a parked tab is a native one that you answer. The guard also refuses any click on an `[AA ...]` marker of the extension.
- **Passwords.** Workers are told never to type a password or create an account. The hooks back this on Google pages (no typing there), and a sign-up name goes to the short extra check, which is told to block a click that creates an account with an email and a password, and which refuses the click when it cannot run at all. A name that states neither way ("Register" on its own) is that check's judgement, not a rule. The name alone no longer decides, because "Register interest" and "Sign up for alerts" create no account and no word tells them from a real sign-up button. On a sign-in provider's own page nothing reaches that check: every click there except a checkbox, radio button or option is refused outright. On other sites the rest is the worker's instruction.
- **You submit.** Workers park every form before the final button. You review it and press Submit.
- Text copied from job pages and forms is treated as data, never as instructions. Without an `ohmyjob.json` in or above the folder, the hooks do nothing.
