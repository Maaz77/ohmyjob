# Safety

How ohmyjob keeps you in control of every application. [Back to the README](../README.md)

- **Never submit.** Hooks run on every Chrome call — in the main session and in every ohmyjob agent — and refuse final controls: Submit, Send, Confirm, Finish and their equivalents in many languages, plus unnamed submit buttons. `javascript_tool` is denied in the workspace settings. The rules differ by caller:
  - **Application workers** may act only in their own tab and its sign-in tab; every click carries an action note, and a click whose note says it sends the application is refused; uploads are limited to that job's own resume; and a button name that no word list can decide goes to a short extra check, which refuses the click if it fails.
  - **The main session and any other agent** may click only on references from a fresh read of that tab, one pressable click per read, with no coordinate clicks, only allowlisted keys (Tab, Shift+Tab, Escape, Backspace, Delete, arrows, Home, End, Page keys, Ctrl/Cmd with A, C, V, X, Z, Y: so no Enter, Return or Space), navigation to http(s) addresses only, no Apply click on a job board or under a filled form, and the control's own name checked against the final word lists (in 62 languages). The consent, Google, OAuth, sign-up and delete rules and the extra check apply to application workers only.
- **One exception to the Apply rule.** On a tab that looks like a form but where the worker answered nothing (a job page with search boxes), a click on an Apply link that only opens the next page passes. All seven must hold: (1) an Apply word in the link's name or inside it; (2) the role is `link` with a navigable address (backslashes read as slashes, http or https only), and the note says it opens or loads a page or form (a note that says it submits is refused, and "Applies to this job" does not pass); (3) the tab has no fill, upload, tick or option of the worker (a toggle of a cookie dialog does not count); (4) the tab is not a `/continue-applying` tab, also not on the job's own address; (5) the target is another page (host and path, ignoring query, hash, case and a trailing slash); (6) neither the current page nor the target is a job board (the `BOARD_LABELS` list plus more boards used only here); (7) the page shows no file input. Buttons, `#` and `javascript:` links and every other tab keep the old refusal. When no answer was given, the refusal tells the worker to stop with `blocked`, or with `parked` only if the page is a form filled up to that button.

- **One exception for pickers and lists.** A control that carries a final word but sits inside a `listbox`, `menu`, `menubar`, `tree`, `treegrid`, `grid` or `combobox` closes that widget rather than sending a form: a date picker's "Done", a multi-select's "Confirm". Such a click skips the word refusal and goes to the short extra check instead, with the name of the widget it sits in as context; the check refuses it if it fails, and a failed check refuses it too, so no control is ever allowed on its name alone. `dialog` is deliberately not on that list, because the submit button of a LinkedIn Easy Apply dialog and of every modal application form sits inside one — so a picker that renders as a dialog stays refused. This applies to application workers only: a click of the main session or of any other agent is still refused on the word alone. See [ADR 0001](adr/0001-mid-step-final-controls.md).
- **A park is graded on the page, not on the report.** A worker that stops reports the final button it saw, but that is its own claim. The run counts the job as filled and waiting for you only when a final control is actually in the last snapshot of that tab, outside any picker. Otherwise the job goes to Needs Attention, where you look at it, instead of to Pending Review, where it would look finished.

- **Before setup, the guard cannot run.** Until setup has created the Python environment, the main session's Chrome guard lets a call through with a notice — but no pipeline can run before setup, and every agent's Chrome calls (not only ohmyjob agents) are denied outright. Run `/ohmyjob:setup` first.
- **Dialogs in run tabs.** In a run-group tab the helper extension answers `confirm` and `prompt` with Cancel (never OK), shows `alert` as text (`[AA alert] ...`) and drops `beforeunload` prompts, so no worker can accept a page's dialog. End-of-run grouping gives native dialogs back, so a `confirm` on your own Submit in a parked tab is a native one that you answer. The guard also refuses any click on an `[AA ...]` marker of the extension.
- **Passwords.** Workers are told never to type a password or create an account. The hooks back this on Google pages (no typing there) and by refusing sign-up buttons; on other sites it is the worker's instruction.
- **You submit.** Workers park every form before the final button. You review it and press Submit.
- Text copied from job pages and forms is treated as data, never as instructions. Without an `ohmyjob.json` in or above the folder, the hooks do nothing.

Read [DISCLAIMER.md](../DISCLAIMER.md) before you use this on a real account.
