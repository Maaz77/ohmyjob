---
name: edit-template
description: Change the LaTeX resume or CV template from a request in plain words, for example "add a section Selected Projects to the resume" or "make the accent colour of the CV blue". Works out whether the request is for the resume, the CV or both, edits the workspace copy of the template, and builds the two sample templates to prove it still compiles. Use only when the user types /ohmyjob:edit-template <request>.
disable-model-invocation: true
allowed-tools: Bash(ohmyjob *), Read, Edit, Write, AskUserQuestion
---

Change the resume or CV template as the user asked now. The request is `$ARGUMENTS`. If it is empty, ask the user in one short question what they want to change, and stop until they answer.

A line of output that starts with `ohmyjob: ` or `FATAL` is an error: show it as it is and stop. Never edit `awesome-cv.cls` (the vendored Awesome-CV class: its licence forbids a modified copy under the same name), the Python scripts, a job's tailored yaml, or the user's own role yamls: only the user changes their resumes. If the request is about something else (what the screening or the tailoring does, the job search), say this command only changes how the resume and the CV look and what sections they have, and stop.

## How the template works (read this before you decide anything)
- One file makes both documents: `resume.tex.j2`, a Jinja template that prints LaTeX. It branches on `document` (`"resume"` or `"cv"`). Jinja delimiters are `<% ... %>` for statements and `<< ... >>` for values, never braces.
- The user's editable copy is `ohmyjob/Resume_Template/resume.tex.j2` in the workspace. Builds use it instead of the plugin's file when it exists, and a plugin update never replaces it. Edit only this copy.
- The sections each document has, their order and their headings come from the yaml and are fixed by the plugin: resume = Summary, Work Experience, Honors & Awards, Certificates, Education; CV = Education, Skills, Experience, Extracurricular Activity, Honors & Awards, Certificates, Presentation, Writing, Program Committees. The template's `for key in order` loop prints them.
- Inside the template these are available: `document`, `accent`, `name.first`, `name.last`, `title`, `headings`, `lists`, `order`, `experience`, `education`, `skills`, and `data`, the whole yaml as the user wrote it (a plain mapping: read a key with `data.get("key")`, never `data.key`, which fails when the key is missing).
- Every value must go through a filter: `|plain` for a heading or a header field, `|tex` for text that may hold `**bold**`, `|cvitems` for a list of bullets. Never print a yaml value without one, never add `\input`, `\write18`, `\openin` or any command that reads or runs something: yaml text is data from a model.

## 1. Find out which document
Decide from the words of the request: "resume" or "résumé" means the resume, "CV" or "curriculum vitae" means the CV, "both", "all" or "my documents" means both. If it does not say, or names neither, look at the `document:` line of the yamls in `Default_Resume_Files/` (Read them; only the first lines are needed): if they are all one kind, say which one you assume and ask the user to confirm. If they are mixed or none exists, ask with AskUserQuestion: Resume, CV, or both. Never guess. A change for one document is wrapped in `<% if document == "resume" %> ... <% endif %>` (or `"cv"`); the other document must come out exactly as before.

## 2. Get the editable copy
Run `ohmyjob resume template`. It prints `TEMPLATE <path>` and creates the copy from the plugin's file only when it is missing (an existing copy keeps the user's earlier edits). Read that file in full before you edit it.

## 3. Make the change, in the smallest edit that does it
- **Colour.** `\colorlet{awesome}{awesome-<< accent >>}` sets the accent. The colours that exist are `emerald`, `skyblue`, `red`, `pink`, `orange`, `nephritis`, `concrete`, `darknight`. For a named colour, replace `<< accent >>` with that name (for one document: an `<% if document == ... %>` around two `\colorlet` lines). "Blue" means `skyblue`: say so. For an exact shade ask for or use a hex value and write `\definecolor{awesome}{HTML}{RRGGBB}` in place of the `\colorlet` line. Tell the user that the `accent_color` key of their yamls no longer changes that document's colour.
- **Layout and style.** Page margins are the `\geometry{...}` line; fonts are the `\setmainfont`, `\setsansfont` and `\renewfontfamily\roboto` lines (keep `Renderer=Node`: it keeps plain hyphens in the PDF text, and use only fonts the TeX installation has, otherwise the build fails); the header is the `\name` ... `\makecvheader` block; the footer is `\makecvfooter`. Changing margins, font size or font changes how many characters fit on a line: say that the one-line bullet limit of about 124 characters (and 109 for skill rows) may no longer hold, and that the page count may change.
- **A section that already exists.** Change its block in the `for key in order` loop. To rename a heading, tell the user to add a `sections:` key to their yaml (for example `sections: {experience: Career}`): the yaml owns the headings and the user's file is theirs. To drop a section, tell them to delete its key from the yaml: the build leaves out a section without entries.
- **A new section** (for example "Selected Projects"). Choose a yaml key in lower case with underscores (`selected_projects`; never `projects`, `interests`, `introduction` or any key already used), print it from `data.get("selected_projects")` inside `<% if data.get("selected_projects") %> ... <% endif %>` so a yaml without the key prints nothing, and copy the look of the closest existing section (`\cvsection{...}` then `cventries` with `\cventry{position}{title}{location}{dates}{description}` for entries with bullets; `cvhonors` with `\cvhonor{award}{event}{location}{date}` for one-line items; `cvparagraph` for text). Put it where the user said, in one of two ways: right after an existing section, with `<% if key == "experience" %> ... <% endif %>` after the whole `if/elif` chain inside the loop (it shows only when that section has entries); or before or after the loop for a fixed place. Restrict it to the requested document with `document`. Because the key is not one the plugin knows, a tailored resume never changes it (it is copied as it is) and `/ohmyjob:master-resume` does not merge it: tell the user.
- A request the template cannot express (a new header field that needs a class command that does not exist, a different class): say so and offer the closest thing; do not edit the class.

## 4. Add the sample to the templates
When you added a section or a key, add the same key to `ohmyjob/Default_Resume_Files/Template.yaml` and/or `Template-CV.yaml` (the one for the document you changed), with a comment line starting `# optional:` and one or two mock entries in the same style as the file, so the user can copy it. Edit only these two files, never a role yaml, and never touch their first line (the template marker).

## 5. Prove it builds
Run `ohmyjob resume build "<workspace>/Default_Resume_Files/Template.yaml" --out "<workspace>/.ohmyjob/edit-template/Template.pdf"` and the same for `Template-CV.yaml` and `Template-CV.pdf` (use the workspace path printed in step 2, the folder above `Resume_Template/`). Build both, even when only one document changed: the other must still compile. Each prints `OK <pdf>` or `FAIL <reason>`. Then Read the built PDF of the document you changed and look at it: the change is there, nothing overlaps, no text is cut.
- `FAIL`: read the reason, fix your edit and build again. After three failed builds, or if a fix is not clear, run `ohmyjob resume template --reset` (it deletes the copy: the default template is used again), say what failed, and stop. Never leave a template that does not build.
- A change that must be undone later: `ohmyjob resume template --reset` removes every edit and returns to the plugin's template (the yaml sample lines of step 4 stay; they are harmless).

## 6. Report
Tell the user, in short lines: which document(s) the change is for and why you decided so; what you changed in `ohmyjob/Resume_Template/resume.tex.j2` (one line); which sample you added to which `Template*.yaml`; what they must do in their own role yamls, if anything (copy the new key from the sample, or set `sections:`); and that `/ohmyjob:build-resumes` rebuilds their PDFs with the new template (a tailored resume keeps the page count of its source PDF, so rebuild each one before `/ohmyjob:prep-jobs`). End with: `ohmyjob resume template --reset` undoes all template edits.
